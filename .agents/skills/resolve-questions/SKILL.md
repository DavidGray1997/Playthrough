# Resolve SDLC questions and assumptions

Read the [shared SDLC contract](../sdlc/references/document-contract.md) and [question record rules](references/question-records.md) before acting. Resolve the project root, initiative, requested phase filter, and existing conventions. Read the relevant phase logs, linked decisions, and affected records. Use only phase `questions.md` files for tracking; report to the user in chat. Do not create handoff or reconciliation files.

## Capture and discover

Each skill records questions and unconfirmed assumptions it raises in the owning phase's `questions.md`, using the [template](assets/questions.md). When called by another skill, preserve that originating skill as the raising skill. Preserve one owning entry and link it from other records/phases that depend on it. Record actual timestamps, concerned skills, record links, answer options and their implications where practical. An assumption can offer approval, rejection, or correction. Mark suggested answers as recommendations; never silently select one.

When asked what is open for an initiative, read all four phase logs. Apply an optional requirements, design, build, or release filter to the owning phase; also identify relevant dependencies owned elsewhere without duplicating their entries. Include unresolved questions, unconfirmed assumptions, deferred items, and a separate list of answered items whose reconciliation is unfinished. Show ID, phase, statement, kind/status, options where useful, and blockers. Distinguish missing logs from confirmed empty logs. If legacy documents contain untracked open items, report those with source links; a listing alone does not authorize creating or migrating logs.

After the list, ask whether the user wants to be guided through resolving it. Do not start the interview merely because a list was requested. If guidance was already requested, start with the first dependency or blocker instead of asking again. If no unresolved items or unfinished reconciliation remain, say so without offering an empty interview.

## Keep the interview within the current phase

Before adding a requirements interview row, distinguish an unresolved product-owner choice from the mechanism for delivering agreed behaviour. Ask about product scope, business rules, security/privacy obligations, acceptance outcomes or explicit user constraints. Route implementation mechanisms to the appropriate design or operations record: for example ranking/scoring formulas, codec and input/control limits, exact UI, provider/FX/retry/date mechanics and operational procedures. If a mechanism materially changes user-visible behaviour, money, access, privacy or a user constraint, ask only about that product consequence and leave its implementation to design. Respect an explicit request to discuss design or another phase.

Maintain a finite current-phase queue of distinct unresolved owner decisions, each mapped to its owning stable ID and subdecision. Review legacy notes by meaning; do not turn every note or technical detail into a new interview question. Distinguish individual decisions from umbrella topic groups when reporting counts. Remove settled decisions from the active queue without deleting their history. Add a genuinely new requirement, contradiction or unanswered dependency only with its evidence, reason and effect on the remaining count; do not silently grow the queue or invent rows to fill a batch. Keep deferred design/operations details outside the requirements interview without treating them as approved or completed.

Report actionable questions remaining separately from reconciliation blockers and final approval checkpoints. Once no substantive requirements choices remain, finish reconciliation, consolidate the PRD through [write-prd](../write-prd/SKILL.md), and present concrete reviewable content for its normal product-owner approval checkpoint. Do not restart the interview to settle technical details. If missing evidence or an unresolved product consequence blocks that checkpoint, identify that specific blocker instead of implying approval or manufacturing further questions.

## Guide and record answers

Guide resolution in concise batches of five questions, or all remaining questions when fewer than five remain. Respect an explicitly requested different batch size or interaction style. Select actual unresolved choices from the records, prioritising dependencies and substantive decisions for the current phase; do not repeat settled choices, invent gaps to fill a batch, or turn later design details into requirements-interview questions.

Use this same Markdown table format for every batch:

| # | Question | Suggested answer (A) | Alternative B | Alternative C |
|---|---|---|---|---|
| 1 | One concise, concrete decision. | A clear recommendation. | A distinct viable alternative. | A second distinct viable alternative. |

Number each batch from 1 to 5, with one decision per row, and give exactly two useful alternatives to the suggested answer. Keep each cell short and self-contained; use consistent project terminology. Make recommendations explicit proposals awaiting approval, not defaults already adopted. If a choice genuinely needs free text or evidence rather than alternatives, retain the table format, explain that briefly in the row and request the needed input instead of inventing misleading options. After the table use: `Reply “approve all”, or give changes such as “2B, 3C; approve the rest.”`

Map each displayed row number to its owning phase question/assumption ID and exact subdecision. Preserve that mapping in the owning phase log when maintaining the records; display numbers do not replace stable record IDs. Accept bulk approval, numbered options, plain-language changes, clarification questions and individual answers. Treat an unambiguous numbered “approved” or “yes” as approval of that row’s suggested answer only. A clarification question is not approval; explain it concisely, record independently clear answers and keep that row unresolved. Allow deferral without treating it as approval or resolution. For an assumption, approval alone can answer it; record corrections or rejection exactly within their stated scope.

After every row in the current batch has been answered and the answers reconciled, briefly report the recorded outcome and immediately present the next batch in the same response. Do not wait for “next” or ask permission to continue. If any row needs clarification, finish reconciling the independent answers and resolve that row before starting a new batch. If fewer than five unresolved choices remain, show only those. Stop when no actionable unresolved choices or unfinished reconciliation remain in the requested scope, or the user pauses/stops; say when the interview is complete. Identify deferred items, pending approval checkpoints or concrete reconciliation blockers separately rather than claiming the initiative is fully approved or inventing more questions.

Bind each response to its item ID and answer revision. A response naming an ID can be processed directly without an interview. Clarify genuinely ambiguous mappings before changing the record. Record the answer, actual response timestamp, authority/source as a role or pseudonymous ID, and any supporting evidence. Preserve prior responses when an answer changes; increase its revision and supersede the old response. A material choice or changed approved decision also goes through [record-decision](../record-decision/SKILL.md), with links in both records. A factual answer does not require a fabricated decision.

Choose the decision's owning phase by its meaning and the established authority record, not by the question's location. Product scope and business rules belong in requirements decisions by default, even when a design skill raised the question; design mechanisms belong in design decisions. Link one authoritative decision from other phases. Record an additional phase decision only for a distinct choice or effect, with an explicit relationship; do not duplicate the same approval in several logs.

An answer, approval, rejection, or correction triggers reconciliation immediately. The user's request to resolve questions authorizes directly affected SDLC documentation maintenance; it does not authorize implementing code, deployment, publication, external tickets, or messages. If the answer conflicts with existing approval or leaves a dependent choice unclear, record the evidence, flag the specific conflict, and seek only the missing authority or information. Continue independent authorized reconciliation.

## Reconcile through concerned skills

1. Mark reconciliation pending for the answer revision. Determine impact from the raising skill, concerned skills, linked requirements/stories/decisions, and downstream records. Inspect dependencies rather than relying only on the original concern list. Read the applicable specialist instructions before carrying out their work. Use the [SDLC routing map](../sdlc/SKILL.md) to find record owners; update the concern list with reasons if new impacts emerge. For a non-skill/user-raised item, route through the relevant record owner.
2. In the entry's reconciliation table, record each skill, affected canonical record/section, dependency, expected adjustment, status, and evidence. Include the raising skill; a review may conclude that no record change is needed, with rationale. Do not expand into unrelated record creation or implement code under documentation scope. Mark implementation-dependent evidence stale or pending, and update the existing backlog/verification/release record when applicable.
   A missing target is not a reason to invent a full design or scaffold another phase. Create a missing affected record only when the current assignment includes its creation and lifecycle prerequisites permit it; otherwise record the missing target, the needed creation/checkpoint, and pending or blocked reconciliation. This does not prevent creating the owning question log or the directly required decision entry. Capture the answer's effect there without claiming absent records were updated. Normalize a partial legacy entry in place when resuming authorized work; preserve its ID, known timestamps, answers and evidence rather than duplicate it.
3. Prefer subagents for independent skill work when available and permitted. Give each the initiative, exact item ID and answer revision, response evidence, applicable skill path to read, affected records, permitted write ownership, and expected result. Assign disjoint records; the coordinator alone edits shared `questions.md` and `decisions.md` logs and allocates IDs. Workers return proposals for shared-log changes in their messages, without creating files for handoff. When several skills own overlapping records, use sequential work or parallel read-only proposals followed by coordinator edits. Run upstream work first when downstream work depends on it. If delegation is unavailable, run the same specialist work sequentially.
4. Workers re-enter their assigned specialist skill with the answer as new evidence. They read its instructions and relevant question entries, reconcile only assigned records, and report changed sections, remaining uncertainty, invalidated evidence/approvals, and any new questions. During an active reconciliation, route new answers and new questions back to the coordinator; do not recursively start competing reconciliation runs or allocate shared IDs in workers.
5. Wait for every assigned result. Inspect all edits/proposals, reconcile cross-record conflicts, update related decisions through record-decision, and verify links, stable IDs, answer revision, factual consistency, and accurate evidence/approval status. Re-read records after sequential dependency changes. A changed answer makes results for its prior revision stale; revisit only affected work. Resume unfinished work from its recorded state rather than duplicate completed changes or decisions.
6. Mark reconciliation complete only when every affected skill has an evidenced completed adjustment or justified no-change review and affected records agree. If work cannot continue, retain pending/blocked state, identify the exact blocker and needed action in the owning entry, and report incomplete reconciliation plainly. Introduce further unresolved questions as linked entries; an answer cannot be reported fully reconciled while a new blocking dependency remains. Where the answer affects no records, mark reconciliation not needed with an impact-review rationale.

Keep response state and reconciliation state separate. Do not delay recording a valid answer because some downstream work is blocked, or claim an answered question is fully settled before reconciliation finishes. In guided mode, briefly report resolved IDs, changed records and any reconciliation blockers, then follow the batch progression above; pause for the current batch’s answers or clarification, not permission to present an already-authorised next batch. At completion, distinguish resolved work from deferred items and pending initiative checkpoints.
